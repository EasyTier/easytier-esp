# EasyTier-ESP 硬件联调指南

本指南用于把 `easytier-esp` 组件跑上真实硬件，并按可复现的步骤验证 M0~M4 的验收项。
PC 侧的宿主测试与 IDF 构建只能覆盖协议与算法逻辑，**设备侧的真实行为**（PSA/mbedTLS、
lwIP 网卡、任务栈与内存、与上游 EasyTier 的互操作）必须按本指南在板子上验证。

---

## 0. 前置条件

| 项目 | 要求 |
| --- | --- |
| 开发板 | ESP32-S3（示例按 8 MiB Octal PSRAM 配置；无 PSRAM 也能跑，但内存更紧张） |
| ESP-IDF | **6.1.x**（`source ~/.espressif/tools/activate_idf_v6.1.sh`） |
| 物理网络 | 开发板能上网的 WiFi；一台与板子同网段可达的 Linux 机器 |
| 对端节点 | Linux 上的上游 EasyTier（`easytier-core` + `easytier-cli`） |

拓扑（下文一律用这个命名）：

```
[ESP32-S3  10.144.144.10] ──TCP──▶ [Linux 入口 10.144.144.20] ──▶ 其他节点
        esp-demo / <secret>            esp-demo / <secret>
```

虚拟网段固定用 `10.144.144.0/24`（上游默认之一）。**务必确认它与你的物理局域网不重叠**：
重叠时组件会拒绝创建虚拟网卡并打印
`virtual subnet overlaps the physical LAN`。

## 3. 步骤二：准备 Linux 入口节点

```bash
# 1) 启动入口节点（首次运行需要 root 创建 TUN）
sudo easytier-core --network-name esp-demo --network-secret 'replace-with-your-secret' \
     -i 10.144.144.20
# 默认监听 tcp://0.0.0.0:11010 与 udp://0.0.0.0:11010
# 也可以用 TOML（与本组件相同的上游格式）：
#   instance_name = "linux-entry"
#   ipv4 = "10.144.144.20"
#   [network_identity]
#   network_name = "esp-demo"
#   network_secret = "replace-with-your-secret"
#   sudo easytier-core -c /etc/easytier/entry.toml

# 2) 确认本机状态
sudo easytier-cli node      # 本节点 peer_id / 虚拟 IP
sudo easytier-cli peer      # 已建立的 peer 列表（应出现 ESP 的 hostname）
sudo easytier-cli route     # 路由表（应出现 ESP 的虚拟 IP 与下一跳）
```

注意事项：

- 防火墙需放行 **TCP 11010**（本组件只主动发起 TCP 连接，不监听端口）。
- 入口节点与 ESP 的 `network_name` / `network_secret` 必须**完全一致**，否则握手会被
  拒绝（日志表现为 `handshake rejected` / 反复重连）。
- `-i` 是静态虚拟 IPv4；若想用自分配，改用 `-d`（dhcp）。

## 4. 步骤三：配置并烧录示例

1. 配置 WiFi 与示例参数：

```bash
idf.py menuconfig
#   Example Configuration → WiFi SSID / Password
#   Example Configuration → Enable embedded EasyTier TOML（默认开启）
```

2. 按你的环境修改 [`main/easytier.toml`](../main/easytier.toml) 的三处：

```toml
ipv4 = "10.144.144.10/24"                     # 本机虚拟地址，不能与物理网段重叠
[network_identity]
network_name = "esp-demo"                     # 与 Linux 节点一致
network_secret = "replace-with-your-secret"   # 与 Linux 节点一致
[[peer]]
uri = "tcp://192.168.1.20:11010"              # 改成 Linux 入口节点的可达地址
```

3. 烧录并观察日志：

```bash
idf.py -p /dev/ttyACM0 flash monitor
```

期望的日志序列（**每一步都可独立判定成败**）：

| 顺序 | 日志关键字 | 含义 / 失败时应检查 |
| --- | --- | --- |
| 1 | `wifi disconnected, reconnecting` → `got ip: 192.168.x.y` | WiFi 已拿到物理地址；拿不到就检查 SSID/密码/信号 |
| 2 | `config: instance=... network=...` | **生效配置**（TOML 的映射结果）；network 不对就是 TOML 没生效 |
| 3 | `config: peer[0]=192.168.1.20:11010` | 入口地址解析正确；缺行说明 `[[peer]].uri` 写法有问题 |
| 4 | `easytier started, peer_id=0x........` | 三个任务已启动，peer id 已生成 |
| 5 | `peer connected: 0x........` | **握手成功**（M1 验收）；反复出现说明密钥/网络名不一致 |
| 6 | `dhcp assigned virtual ip=...`（仅 dhcp 模式） | M4 的地址自分配生效 |
| 7 | `network ready: N reachable peer(s)` | **路由同步完成**（M3 验收） |
| 8 | `status: state=ready ... routes=N`（每 10 s 一行） | 稳态观测：直连数、可达路由数、丢弃计数 |

其中第 8 行的 `dropped=` 是重要的健康指标：稳态下它应当**停止增长**；持续增长说明有
报文因无路由/认证失败被丢弃。

## 5. 步骤四：连通性验证

在 Linux 入口节点上：

```bash
ip addr show tun0                 # 虚拟网卡与虚拟地址
ping -c 3 10.144.144.10           # 直连场景：ESP 的虚拟 IP
sudo easytier-cli route | grep 10.144.144.10    # ESP 的下一跳应为直连
```

在 ESP 上（若你的固件包含 ping 应用；否则用组件日志判定）：

```bash
# 控制台没有 shell 时，用 Linux 侧发起的流量验证：
#   ESP 侧 status 行的 direct/routes 会变化，dropped 不应增长
```

**经中继的三节点验证（M4 验收项）**：再启动一个 Linux 节点 C（例如另一台机器或同一台
机的第二个实例，`--network-name/-secret` 相同），让它只与 B 相连：

```bash
sudo easytier-core --network-name esp-demo --network-secret '<secret>' -i 10.144.144.30 \
     -p tcp://<B的IP>:11010
ping -c 3 10.144.144.10           # 从 C 直接 ping ESP：spoof 经 B 中继
sudo easytier-cli route           # C 上到 ESP 的下一跳应为 B（而不是直连）
```

判定要点：C→ESP 的 ICMP 能通、ESP 的 `status` 行 `routes=` 增到 2（B 与 C），且 B 上
`easytier-cli peer` 能看到两侧节点。

## 5.5 人工核对互操作结果

执行上面的直连/中继步骤后，结合两端的实际流量和日志判断：

- 握手成功、`state=ready`、虚拟地址非空且与实际网卡一致。
- Linux 侧路由表包含 ESP 节点；直连和经中继的双向流量均能到达。
- 持续运行至少 5 分钟，无异常重启、看门狗超时或持续丢包。
- 手动断网、恢复后重新握手和同步；只经断开连接可达的路径正确撤销。
- 若出现 ELF checksum mismatch，先确认监控使用的 ELF 与板上固件匹配。

单靠出现 `network ready` 或丢弃计数不增长，不能证明端到端数据通信成功。

## 6. 排错表

| 症状 | 可能原因 | 处理 |
| --- | --- | --- |
| `easytier config rejected: 0x...` + `config issue ...` | TOML 语法错误或必填项缺失 | 看紧随其后的 `key=`；组件会把行内错误定位到键名 |
| `ignored config: key=...` | 该参数上游格式合法但本组件不支持（如自定义加密算法、监听端口） | 属预期行为；确认关键项（network/peers/ipv4）没有在列表里 |
| `wifi reconnect attempts exhausted` | 示例按 `EXAMPLE_WIFI_MAX_RETRY` 放弃重连，组件会停在 `waiting-underlay` 且不再重连 | 调大该配置或设为 0（无限重试）；恢复 WiFi 后只要再次拿到 IP，示例会自动重新通知组件就绪并重连入口 |
| 一直是 `state=connecting` | 入口地址/端口不可达、防火墙拦截 | 在板子同网段用 `nc -vz <ip> 11010` 验证；确认 Linux 侧监听 TCP |
| 反复 `peer connected` 后立即 `peer disconnected` | `network_secret` 或 `network_name` 不一致 | 两端逐字节对齐（注意引号与空格） |
| 一直 `state=syncing` | 已握手但没有路由信息（对端未回同步响应） | 确认对端是**同网络**且允许该节点；查看两端 `dropped` |
| `virtual subnet overlaps the physical LAN` | 虚拟网段与 WiFi 网段重叠 | 改用其它虚拟网段（如 `10.144.144.0/24`） |
| `config: 既没有静态 ipv4 也没有启用 dhcp` | TOML 里两个都没配 | 配 `ipv4 = "..."` 或 `dhcp = true` |
| Linux 侧 `easytier-cli peer` 看不到 ESP | 握手未成功，或 ESP 的 TCP 连接被 NAT/防火墙丢弃 | 先解决上面两行；确认板子能访问入口 IP |
| `ping` 虚拟 IP 不通但 `peer` 可见 | 路由未收敛（`state` 未到 `ready`）或地址不在同一虚拟网段 | 检查 `status: routes=` 是否 ≥1；确认两端 ipv4 同网段 |
| `dropped` 持续增长且 `state=ready` | 数据面找不到目的节点或转发计数超限 | 看是否在 ping 一个不存在的虚拟 IP；确认拓扑已包含目标节点 |
| 吞吐异常低（如几十 B/s） | 多连接下每槽写入预算被均分错误（已在 v9 修复） | 升级到当前版本；`slot 0/1` 各自应能连续发送 |
| `NetworkReady` 事件里虚拟地址为 0 | 事件状态取的是配置而非实际生效地址（已在 v9 修复，dhcp 节点尤其明显） | 升级到当前版本；用 `status:` 行的 `vip=` 复核 |
| 启动即重启 / `A stack overflow in task et_proto` | 任务栈不足（新增缓冲导致） | 跑 `python3 tools/check_stack_usage.py`，把大缓冲移到 `Context`/`SyncEngine` 成员 |
| `malloc` 失败 / 启动日志无 `runtime context` | 常驻内存不足（未启用 PSRAM） | 启用 PSRAM，或减小帧队列/重组缓冲 |
| MTU 相关丢包（大包不通） | 虚拟 MTU 1380 与上层分片不匹配 | 保持 ≤1380；本组件不重组 IP 分片 |

## 6.5 组件日志 → 判定 → 处理（按日志原文索引）

排错时可直接用下面这些**组件原文**定位问题（`grep` 一下日志即可）：

| 日志原文（片段） | 含义 | 处理 |
| --- | --- | --- |
| `easytier config rejected: 0x...` + `config issue N key=...` | TOML 被拒绝（示例打印错误码与出问题的键） | 按 `key=` 修配置；语法错误先看行号 |
| `ignored config: key=...` | 该键上游合法但本组件不支持（如 `listeners`、`flags.*`） | 属预期；确认关键项（network/peer/ipv4）不在列表里 |
| `another instance is already initialized` | 已有实例占用（全组件仅允许一个） | 复用同一实例或先 `deinit()` |
| `context allocation failed (99248 bytes); enable PSRAM or shrink buffers` | 常驻内存分配失败，最常见原因是**未启用 PSRAM** | 启用 PSRAM（示例 sdkconfig 已启用）或减小 Kconfig 上限 |
| `queue/semaphore allocation failed (need ~24 KiB of heap)` | 队列创建失败 | 释放内存后重试；检查是否有其它大块分配 |
| `cannot create et_io task (stack 6144 bytes)` 等 | 三个任务之一创建失败（含所需栈） | 内存不足；先停掉其它占内存的应用 |
| `TcpConn slot N allocation failed (needs ~12 KiB each)` | 连接槽缓冲分配失败 | 同上；或把并发入口数降到 1 |
| `virtual subnet overlaps the physical LAN, refusing to touch the netif` | 虚拟网段与 WiFi 网段重叠 | 换虚拟网段（如 `10.144.144.0/24`） |
| `handshake rejected: N` | 握手校验失败（网络名/密钥/peer 冲突） | 两端 `network_name`/`network_secret` 逐字节对齐 |
| `slot N lost 5 ping responses, closing connection` | 保活判定对端失联（2 秒超时 × 连续 5 次） | 检查链路质量/对端是否退出；这是**预期**的断链检测 |
| `peer N changed session id, clearing its saved route info` | 对端重建了路由会话 | 预期行为；随后会重新同步 |
| `route peer info too large (N bytes)` | 对端节点信息超过 512 字节上限 | 该节点宣告内容过大（例如大量代理网段）；本组件会拒收该条 |
| `underlay ready, reconnecting entry peers` | 物理网络恢复，正在按 1 秒节奏重连 | 正常；若持续出现说明链路抖动 |

## 7. 需要反馈的证据

联调时请一并记录：

1. 设备启动到稳态的完整日志（含 `config:`、`easytier started`、`network ready`、`status:` 行）；
2. `runtime context: ... bytes` 这行（内存预算核对）；
3. Linux 侧 `easytier-cli node / peer / route` 的输出；
4. 失败时的最小复现：哪一步、什么现象、`status:` 行的 `dropped` 是否增长；
5. 若设备侧测试有 `FAIL`，请附该用例名与失败断言。

## 8. 当前已知限制（联调时需要知道）

- **并发入口连接数上限 2**：配置可写最多 10 个入口，前 2 个各占一个连接槽并发连接，
  其余入口作为失败时的轮换备用（日志里会看到 `slot 0/1 tcp connected`）。
- **只主动连接，不监听**：不创建 TCP 监听端口；`listeners` 参数会被忽略并报告。
- **IP 分片不重组**：虚拟 MTU 上限 1380，分片报文直接丢弃。
- **dhcp 只做本机自分配**：不为其他节点分配地址；启用时默认子网 10.126.126.0/24（可配）。
- **压缩**：只支持不压缩（`None`）；对端使用 Zstd 时按不支持处理并撤销事务。
- **加密**：固定 AES-128-GCM、开启加密（与上游默认一致）。
