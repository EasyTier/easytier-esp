## A. 真实缺陷（建议优先处理）

### A1. `EventType::PeerDown` 永远不会触发

- **位置**：公开头 `components/easytier-esp/include/easytier-esp.h:511`（枚举声明）、
  `:537`（`Event::peer_id` 注释声称"PeerUp/PeerDown 有效"）；
  示例 `main/main.cpp:68` 有 `case et::EventType::PeerDown:`
- **证据**：全仓没有任何 `emit(EventType::PeerDown)` 调用点。断开路径确实会跑
  （`proto_task.cpp` 的 `reset_slot` lambda 里调用了 `ctx.sync.on_peer_down(peer_id)`、
  并 `publish_direct_peers()`），只是**没有向应用发事件**
- **影响**：应用无法感知单个直连 peer 断开，只能靠轮询 `Status::direct_peer_count`；
  公开 API 的承诺与实际行为不一致
- **建议改法**：在 `reset_slot` 里"确实曾经 peer_up"的那一支补
  `ctx.emit(EventType::PeerDown, peer_id)`（注意回调在控制面任务同步执行，
  要放在状态清理**之前或之后保持一致**，避免重入读到中间态）；若判定不需要该事件，
  则应从公开头与示例中移除，不要留一个永远不响的枚举
- **风险**：低。只影响事件回调时序；`reset_slot` 在断开/超时/换入口三处都会走到，
  补 emit 后**可能会连续多次上报同一 peer**，需要按 `peer_up[slot]` 去重（该变量已存在）
- **验证**：真机断开一个入口 peer，确认只收到一次 `PeerDown`；恢复后能重连

### A2. `io_task` 退避封顶晚一步：会出现一次 32 s 重试

- **位置**：`components/easytier-esp/src/io_task.cpp:69-73`（`schedule_retry`）
- **现象**：
  ```cpp
  st.retry_at_ms = now_ms() + st.backoff_ms;   // 先按当前值排期
  st.backoff_ms = (st.backoff_ms >= kMaxBackoffMs) ? kMaxBackoffMs : st.backoff_ms * 2;
  ```
  即"先排期、后翻倍"。序列实际为 `1/2/4/8/16/32/30/30…` 秒，而 `kMaxBackoffMs = 30000`，
  所以第 6 次等待是 **32 s，超出声明的 30 s 上限**
- **影响**：重连比声明慢一拍（仅时间语义，不影响正确性）
- **建议改法**：把两行顺序对调
  ```cpp
  st.backoff_ms = (st.backoff_ms >= kMaxBackoffMs) ? kMaxBackoffMs : st.backoff_ms * 2;
  st.retry_at_ms = now_ms() + st.backoff_ms;
  ```
  并把返回值语义改为"本次实际等待"（当前返回值就是排期用的值，对调后需同步返回
  `st.backoff_ms`）。`et_io` 任务头部注释里的"1/2/4/.../30 秒"就是期望序列
- **风险**：低。只改重连节奏；本来本轮只修正了日志打印的数值（原来打印的是翻倍后的值），
  时序**故意保持原样**以免在无真机验证的情况改变行为
- **验证**：给一个不可达入口，观察日志间隔单调收敛到 30 s 且不再出现 32 s

### A3. `drop_slot` 不递增槽代际

- **位置**：`components/easytier-esp/src/io_task.cpp` 的 `drop_slot()`
- **证据**：槽代际只在**连接建立成功**时递增（`conn_slot.generation.store(generation)`）；
  `drop_slot` 只清 `peer_id`、`session_open`、`connecting`
- **影响**：`frame_sendable()` 对"带代际的帧"按代际匹配，旧代际的迟到帧在同一槽**重新
  连上**后仍可能被认领；下游控制面又靠 `session_generation[slot]` 丢弃过期帧，因此
  目前是"两层保护里少了一层"，靠上层兜住
- **建议改法**：`drop_slot` 里也把该槽代际推进到下一个全局值（`ctx.generation.fetch_add(1) + 1`），
  保证"代际唯一标识一个会话"这一不变量在断开时也成立；随后检查
  `proto_task.cpp` 里以代际反查槽位（`peer_of_generation`）的逻辑仍然成立
- **风险**：**中**。代际同时被 `proto_task` 用来定位槽位、被 `virtual_netif` 用于标记
  TCPIP 队列项，改递增时机需要重新推演这三处的一致；建议与 A1 一起做并真机回归
- **验证**：断开后立刻重连同一入口，确认不会收到旧会话的 RPC/Data

### A4. 数据面不检查 `Compressed` / `NotSendToTun`，且接受明文 Data

- **位置**：`components/easytier-esp/src/data_task.cpp` 的 `handle_inbound_data()`
  （`encode_peer_manager_header` 调用点约 `:204`；`flags` 只在 `:101-104` 被写入）
- **证据**：入站只检查 `pm_flags::Encrypted`（`const bool encrypted = (hdr.flags & pm_flags::Encrypted) != 0;`），
  从不检查 `pm_flags::Compressed(0x10)` 与 `pm_flags::NotSendToTun(0x40)`；
  未加密的 Data 在"目的为本机"时会直接走 `deliver_to_netif`
- **影响**：
  1. 上游若发来压缩报文（本 profile 不支持），会被当作明文投递到 lwIP，产生垃圾/异常
  2. `NotSendToTun` 语义（不投递到网卡）被忽略——上游 RPC/内部报文带该位时不应当作用户流量
  3. 是否接受明文 Data 是策略选择（关闭加密时上游 `NullCipher` 也会发明文），
     但当前是"隐式接受"，没有明确表达
- **建议改法**：在决策前加两道检查并按策略计数丢弃：
  ```cpp
  if ((hdr.flags & pm_flags::Compressed) != 0) { ctx.dropped.fetch_add(1); return; }
  if ((hdr.flags & pm_flags::NotSendToTun) != 0) { /* 不透传给网卡 */ }
  ```
  明文策略建议显式写成注释 + 一个具名判断，与上游 `NullCipher` 语义对齐后再落到代码
- **风险**：**中**。会改变"哪些报文被丢弃"的行为，需要与上游同版本节点做一次真实同步/转发
  回归；上游 `common.proto` 是位定义的事实来源
- **验证**：真机双节点同步 + 一条跨节点 ping，确认丢包计数不异常增长

### A5. `plan_inbound` 判序：先判本机投递、后判转发计数上限

- **位置**：`components/easytier-esp/src/data/plane.cpp` 的 `plan_inbound()`
  （`hdr.to_peer_id == snapshot.self_peer_id` 分支在 `hdr.forward_counter > counter_limit`
  之前）
- **影响**：目的为本机但 `forward_counter` 已超限的报文会被投递，而不是按"防环兜底"丢弃。
  上游是先按计数丢弃还是先判本机需要重新核对；若上游先判计数，则这里是**行为差异**
- **建议改法**：确认上游顺序后统一；若要先判计数，把两个 `if` 对调即可（纯函数，易回归）
- **风险**：低。需上游源码确认，不要凭直觉改
- **验证**：构造 `forward_counter = counter_limit + 1` 且目的为本机的帧，确认被丢弃

### A6. `prepare_forward` 允许计数 7 → 8

- **位置**：`components/easytier-esp/src/data/plane.cpp` 的 `prepare_forward()`
- **证据**：`if (hdr.forward_counter > counter_limit) return false;` 之后才 `++`。
  当 `counter_limit = 7`、当前值 7 时通过，转发后变成 8，**超出了上限**
- **影响**：防环阈值实际比声明宽 1 跳；配合 A5 可能让环路多绕一跳
- **建议改法**：改成 `if (hdr.forward_counter >= counter_limit) return false;`——
  但要与 A5 一起核对上游是"先判后增"还是"先增后判"，两处必须同向
- **风险**：低，但属协议行为，需与 A5 一并决定
- **验证**：同一帧连续中继，确认最多转发 `counter_limit - 1` 次

### A7. `FrameMessage::slot` 与 `kAnySlot` 已成只写不读的死字段

- **位置**：`components/easytier-esp/src/context.hpp:49,76`；

- **影响**：字段与 `kAnySlot` 常量、`FrameSink::slot` 的传递链全部是死代码；

- **风险**：低。不影响选路（选路本来就不看它）；`FrameMessage` 尺寸可能因对齐不变
- **验证**：构建 + 真机正常组网即可（该字段无行为）

## B. 常驻内存与任务栈优化

> 前提：`Context` 当前实测 **97,240 B**（基线 97,560 B）；`static_assert` 上限 112 KiB。
> 任务栈：`et_io` 6144 / `et_proto` 10240 / `et_data` 8192 B。
> **所有结论都需要真机 `uxTaskGetStackHighWaterMark` 背书**，不要只看静态估算。

### B1. `SyncEngine` 的两个 `ConnList` 成员可合并，省约 4.5 KiB 常驻

- **位置**：`components/easytier-esp/src/route/sync_engine.hpp:217,219`
  （`conn_list_build_` / `conn_list_recv_`），使用点 `sync_engine.cpp:263,360`
- **证据**：`conn_list_build_` 只在 `build_request` 用，`conn_list_recv_` 只在 `merge_request`
  用；两者不可能同时存活（`build_request` 的唯一调用链是 `proto_task.cpp` 的
  `send_sync_request`，`merge_request` 只被 `handle_request` 调用，二者都在**同一个控制面
  任务**里顺序执行，且 `handle_request` 内部不会再调 `build_request`）。实测
  `sizeof(ConnList) = 4,484 B`，两个成员 = 8,968 B，合并后省 **4,484 B**
- **建议改法**：删掉 `conn_list_recv_`，`merge_request` 改用同一个 scratch 成员
  （建议重命名为 `conn_scratch_` 并在声明处注释"不得在 `handle_request` 调用链内再调
  `build_request`"）。附带优化：`sync_engine.cpp` 里 `ConnList& rows = ...; rows = ConnList{};`
  是 4.6 KiB 全量清零，而两个解码入口（`decode_conn_list` / `expand_conn_bitmap`）
  已经各自 `out = ConnList{}`；**但不能整行删**——两个 conn_info 字段都缺时 `rows` 会保留
  上一次的 `count`，正确改法是只写 `rows.count = 0;`
- **风险**：低。不改任何线上字节；唯一风险是将来有人在 `handle_request` 内嵌套调用
  `build_request`（用注释 + 命名约束）
- **验证**：构建 + 双节点路由同步回归；`sizeof(SyncEngine)` 由 35,240 → 约 30,756 B

### B2. `data_task` 出站路径的 1600 B 栈缓冲

- **位置**：`components/easytier-esp/src/data_task.cpp:130` `uint8_t ip_buf[kMaxIpPacket]`
- **证据**：紧接着 `:162` 调 `send_data_frame`，后者在 `:71` 又开
  `frame[16+1600+28] = 1644 B`，同一路径静态峰值 ≈ 3244 B，占数据面 8192 B 栈的 40%。
  而 `Context` 里已有 `data_rx_scratch` / `data_tx_scratch` 正是为"大缓冲不占任务栈"而设
- **建议改法**：把展平缓冲搬到 `Context`（如 `data_ip_scratch`，同时把 `kMaxIpPacket`
  从 `data_task.cpp:37` 上移到 `context.hpp`），`pbuf_copy_partial` 写入其中。
  次选：复用 `ctx.data_tx_scratch.data`——`send_data_frame` 在 `:109` 写该 scratch 之前，
  `:78-97` 已消费完 `ip_packet`，别名安全但依赖隐式顺序契约，必须写注释
- **风险**：中低。字节内容与加密顺序不变；唯一代价是缓冲从内部 SRAM 挪到 PSRAM（略慢）
- **验证**：`-DEASYTIER_STACK_USAGE=ON` 构建 + `uxTaskGetStackHighWaterMark` 对比

### B3. `data_task` 转发路径的整帧 2012 B 栈拷贝

- **位置**：`components/easytier-esp/src/data_task.cpp:207` `FrameMessage out = frame;`
  （配合 `:204-208` 借用 `data_tx_scratch` 只中转 16 B 头）
- **证据**：`frame` 本身就是 `ctx.data_rx_scratch`；`xQueueSend` 内部还会整帧拷贝一次，
  因此 `out` 是纯多余的一份 2012 B 栈拷贝。同项目的 `proto_task.cpp:645-652` 转发 RPC 时
  就是**原地改写 PM 头**
- **建议改法**：
  ```cpp
  encode_peer_manager_header(MutBytes(frame.data.data(), kPeerManagerHeaderSize), hdr);
  frame.to_peer = plan.next_hop;   // 保持最终目的（PM 头）不变，只改使用的连接
  if (xQueueSend(ctx.q_tx, &frame, 0) != pdTRUE) { ctx.dropped.fetch_add(1); }
  ```
  删除 `out` 与那次 `memcpy`
- **风险**：低。`frame.len`、密文、AEAD 尾都不变；`data_rx_scratch` 在下次
  `xQueueReceive` 前不会被改写
- **验证**：真机中继转发回归（A→B→C 的跨节点 ping）

### B4. Ping→Pong 的 1972 B 栈缓冲（可顺带删一个只剩单调用点的函数）

- **位置**：`components/easytier-esp/src/proto_task.cpp:598-602`
  （`pong[kPeerManagerHeaderSize + kMaxPlainPayload]`、`build_pong_packet`、`send_frame`）
- **证据**：`build_pong_packet`（`peer/handshake.cpp:92-105`）**全仓只有这一个调用点**；
  Pong 与 Ping 的 PM 头只差 `packet_type` 一个字节，且 `hdr.len` 与解密后的
  `payload.size()` 相等（未加密时 `frame.len == 16 + hdr.len` 已校验；加密时
  `decrypt_in_place` 会把 payload 收缩到 `hdr.len`）
- **建议改法**（与 `:645-652` 的原地转发风格一致）：
  ```cpp
  hdr.packet_type = static_cast<uint8_t>(PacketType::Pong);
  encode_peer_manager_header(MutBytes(frame.data.data(), kPeerManagerHeaderSize), hdr);
  frame.len = static_cast<uint16_t>(kPeerManagerHeaderSize + hdr.len);  // 关键！
  (void)xQueueSend(ctx.q_tx, &frame, 0);
  ```
  随后可删除 `build_pong_packet`（`handshake.hpp` 声明 + `handshake.cpp` 实现，约 14 行）
- **风险**：**中（协议路径）**。必须逐字节比对：`type/len` 如上，
  `flags/forward_counter/reserved/from/to` 均由原 `hdr` 重编码。**漏掉 `frame.len` 截断**会在
  "对端把 Ping 标为 Encrypted"时多发 28 B AEAD 尾垃圾
- **验证**：宿主/真机对比 Pong 报文的十六进制；确认保活正常、间隔按 1/2/4/…/32 s 退化

### B5. `send_frame` 与主循环每轮的 2012 B 零初始化

- **位置**：`components/easytier-esp/src/proto_task.cpp:58`（`FrameMessage msg{}`）、
  `:511`（主循环 `FrameMessage frame{}` 每轮零初始化）
- **证据**：`send_frame` 的 4 个调用点全部在控制面任务内，`xQueueSend(...,0)` 会同步整帧
  拷贝，因此一个可复用暂存足够；`Context` 已有 `data_rx_scratch/data_tx_scratch` 先例
- **建议改法**：`Context` 增加控制面专用 `ctrl_rx_scratch` / `ctrl_tx_scratch`，
  去掉 `{}`（`xQueueReceive`/`xQueueSend` 会整体覆盖）
- **风险**：中低。收益是控制面栈峰值 −2×2012 B；代价是常驻内存 +4 KiB 且落到 PSRAM。
  **属"常驻内存换任务栈"，是否值得必须看真机高水位**
- **验证**：`uxTaskGetStackHighWaterMark(proto_task_handle)` 前后对比

### B6. `RpcReassembler::Slot` 每次新消息清零 16.6 KiB

- **位置**：`components/easytier-esp/src/rpc/fragment.cpp`（`slot = Slot{}` /
  `*oldest = Slot{}`）、`fragment.hpp` 的 `Slot` 定义
- **证据**：`Slot` 含 `rx[8192] + ordered[8192]` + 小数组，约 16.6 KiB；读取范围只由
  `body_len/received/piece_len/piece_pos/have` 决定，陈旧字节永不被读
- **建议改法**：分配/回收时只重置元数据（`used/key/total_pieces/received/body_len/
  first_seen_ms` + `piece_len/piece_pos/have` 三个小数组），不要整结构赋值。
  进一步可把 `have` 换成 `uint32_t` 位图（`kRpcMaxPieces = 32`，正好一位一片）
- **风险**：低。控制面单线程；乱序/一致重复/冲突重复的判定全部保持
- **验证**：多片 RPC（路由同步本身就会分片）回归 + 乱序注入

### B7. `TcpConn::kRxCapacity` 是最大帧的 2 倍

- **位置**：`components/easytier-esp/src/transport/tcp.hpp:112`
  `static constexpr size_t kRxCapacity = (kTcpTunnelHeaderSize + kMaxTcpBodyLen) * 2;`
- **证据**：`body_len > kMaxTcpBodyLen` 在 `read_available()` 里已直接 `return false`，
  故单帧 ≤ 2004 B；2× 只是"一次 read 后多切几帧"的批处理优化，**不是正确性要求**。
  缩到 1× 每槽省 2004 B，6 槽约 **12 KiB**（`Context::slots` 在堆上）
- **建议改法**：若确定要省内存，把 `kRxCapacity` 收到 `kTcpTunnelHeaderSize + kMaxTcpBodyLen`
- **风险**：**中（性能）**。会增加 `recv()` 次数与 `io_task` 里 drain 循环的触发频率；
  未实测 CPU/吞吐前**不建议改小**
