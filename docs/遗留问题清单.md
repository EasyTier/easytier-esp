## A. 真实缺陷（建议优先处理）

### A1. `EventType::PeerDown` 永远不会触发 —— ❌ 仍存在

- **位置**：公开头 `components/easytier-esp/include/easytier-esp.h:164`（枚举声明）、
  `:190`（`Event::peer_id` 注释声称"PeerUp/PeerDown 有效"）；
  示例 `main/easytier_app.cpp:71` 有 `case et::EventType::PeerDown:`；
  断开路径 `components/easytier-esp/src/tasks/proto_task.cpp:452` 的 `reset_slot` lambda
- **证据**：全仓 `emit(` 只有 `Error`/`Started`/`PeerUp`/`NetworkReady`/`Stopped`，
  **没有任何 `emit(EventType::PeerDown)`**。`reset_slot` 在 `:455-457` 调
  `ctx.sync.on_peer_down(peer_id)`、`:463` `publish_direct_peers()`，但不发事件
- **影响**：应用无法感知单个直连 peer 断开，只能轮询 `Status::direct_peer_count`；
  公开 API 的承诺与实际行为不一致
- **建议改法**：不要像旧文档那样在 `:456` 旁边直接补 emit——那时
  `publish_direct_peers()` 还没跑，事件里的 `status.direct_peer_count` 仍含该 peer，
  与 `get_status()` 不一致（违背 `context.h:196-199` 的注释约定）。**推荐把 emit 放到
  清理与 `publish_direct_peers()` 之后，并用 `peer_up[slot]` 去重**：
  ```cpp
  const uint32_t peer_id = ctx.slots[slot].peer_id.load();
  const bool was_up = peer_up[slot] && peer_id != 0;
  if (was_up) ctx.sync.on_peer_down(peer_id);
  // ...清 peer_up / session_generation / peer_id...
  publish_direct_peers();
  if (was_up) ctx.emit(EventType::PeerDown, peer_id);   // 控制面任务内同步回调
  ```
  若判定不需要该事件，则应从公开头与示例中移除，不要留一个永远不响的枚举
- **风险**：低。`was_up` 保证每条真实断开只报一次（`reset_slot` 被 UnderlayDown/
  Connected/Disconnected/退出四处调用）
- **验证**：真机断开一个入口 peer，确认只收到一次 `PeerDown`；恢复后能重连

### A2. `io_task` 退避封顶晚一步：会出现一次 32 s 重试 —— ❌ 仍存在

- **位置**：`components/easytier-esp/src/tasks/io_task.cpp:69`（`schedule_retry`）
- **现象**：
  ```cpp
  st.retry_at_ms = now_ms() + st.backoff_ms;      // 先按当前值排期
  const uint32_t delay = st.backoff_ms;
  st.backoff_ms = (st.backoff_ms >= kMaxBackoffMs) ? kMaxBackoffMs : st.backoff_ms * 2;
  ```
  即"先排期、后翻倍"。序列为 `1/2/4/8/16/32/30/30…` 秒，而 `kMaxBackoffMs = 30000`
  （`:37`）、`kInitialBackoffMs = 1000`（`:39`），所以第 6 次等待是 **32 s，超出上限**
- **影响**：重连比声明慢一拍（仅时间语义，不影响正确性）；`et_io` 任务头注释
  （`:7` "1/2/4/.../30 秒"）与实际不符
- **建议改法**：旧文档的"两行对调"会把首次等待从 1 s 变成 2 s（序列变 2/4/8/16/30…），
  与注释和初值语义不符。**推荐"先排期、后翻倍并夹紧"**：
  ```cpp
  st.retry_at_ms = now_ms() + st.backoff_ms;
  const uint32_t delay = st.backoff_ms;
  st.backoff_ms = st.backoff_ms >= kMaxBackoffMs ? kMaxBackoffMs : st.backoff_ms * 2;
  if (st.backoff_ms > kMaxBackoffMs) st.backoff_ms = kMaxBackoffMs;
  return delay;
  ```
- **风险**：低。只改重连节奏
- **验证**：给一个不可达入口，观察日志间隔单调收敛到 30 s 且不再出现 32 s

### A3. `drop_slot` 不递增槽代际 —— ⚠️ 形态仍存在，后果被削弱

- **位置**：`components/easytier-esp/src/tasks/io_task.cpp:159`（`drop_slot`）
- **证据**：`drop_slot` 只 close、把 `peer_id` 清零、清 `session_open`、轮换入口并退避，
  **从不写 `conn_slot.generation`**；代际只在连接成功时推进（`:332-333`）
- **影响（复核后收窄）**：
  - `frame_sendable` 按代际匹配，但 `pump_tx`（`:183-196`）先要求
    `session_open && connected()`，断开槽直接被跳过（`:216` 丢弃无匹配帧），
    重连后的代际也是全新的——**旧帧被认领的窗口在当前实现下基本被门控挡掉**；
  - 控制面还有一层 `proto_task.cpp:517-524`（按 `session_generation[slot]` 丢弃过期帧）
    与 `:503-507`（Disconnected 时清理）。
  - **残留的真实影响**在 reconnect 命令路径：`io_task.cpp:265` 用
    `ctx.slots[i].generation.load() == cmd.generation` 反查槽位；断开不推进代际时，
    控制面在收到 Disconnected 之前入队的过期 `Reconnect` 命令仍会命中该槽，
    导致重复 `drop_slot`（再轮换入口、再重置退避）
- **建议改法**：在 `drop_slot` 的 `post_event` 之后推进槽代际：
  `conn_slot.generation.store(ctx.generation.fetch_add(1) + 1);`，
  过期命令随后会被 `:271-273` 正确忽略
- **风险**：中低。`virtual_netif` 用的是 **Context 级**代际（`inst.cpp` 传入
  `&ctx.generation`），不是槽代际，因此不受影响；`peer_of_generation` 只用于
  `handle_rpc_response`，也不受影响。需真机"断开即重连"回归
- **验证**：断开后立刻重连同一入口，确认不会重复 `drop_slot`、不会收到旧会话的 RPC/Data

### B1. `SyncEngine` 的两个 `ConnList` 成员可合并，省约 4.5 KiB 常驻 —— ❌ 仍成立

- **位置**：`components/easytier-esp/src/route/sync_engine.hpp:217,219`

- **风险**：低。不改线上字节；唯一风险是将来嵌套调用（用命名 + 注释约束）

- **位置**：`components/easytier-esp/src/inst.cpp`（构造函数局部 `Settings settings{}`）
- **修复**：构造里加了 `SettingsSecretGuard`，离开作用域时对局部副本调用
  `zeroize_string(network_secret)`；`Context` 析构再清零自己持有的那一份。
  下面保留原始现象记录：
- **原证据**：解析成功后 `settings.network_secret` 持有密钥；成功路径把它拷进
  `ctx_->settings` 后局部对象直接析构，失败路径（解析失败 `:294`、校验失败 `:299`、
  上下文分配失败 `:305`）同样直接返回。**没有任何路径对局部 `settings` 调
  `zeroize_string`**
- **影响**：密钥副本残留在（随后可被复用的）构造函数栈帧上，与"析构清零密钥"的
  安全意图不一致
- **建议改法**：用一个小的 RAII guard，在构造函数所有返回路径上
  `zeroize_string(settings.network_secret)`（例如把 `Settings settings{}` 包进
  `{ Settings settings{}; /* ... */ }` 并加 `struct SettingsGuard { Settings& s;
  ~SettingsGuard(){ zeroize_string(s.network_secret); } };`）
- **风险**：低。只影响失败/成功后的栈残留

### F2. `Inst` 不接受"解析成功但校验失败"时的配置快照 —— ❌ 新增（行为细节）

- **位置**：`components/easytier-esp/src/context.cpp` 的 `Context::get_config_info()`
  与 `inst.cpp` 构造函数校验分支
- **证据**：`get_config_info()` 在 `ctx_ == nullptr` 时返回 `ESP_ERR_INVALID_STATE`；
  而 TOML 解析成功、`validate_config` 失败（如缺 peer / 缺虚拟地址）时 `ctx_` 为空，
  `Settings` 里其实已有完整取值，但实例对外没有可读入口（诊断也已改为只写日志）
- **影响**：应用在这种失败下只能看到 `last_error()`，无法通过 `get_config_info()`
  打印"实际解析出的设置"来定位问题
- **建议改法**：可选——把 `Settings` 留在 `Inst`（而不是只存在于 `Context` 里），
  让 `get_config_info()` 在校验失败时也能给出快照；或者接受现状并在文档里写明
- **风险**：低。属可用性改进

### F3. `std::string`/`std::vector` 分配失败会终止进程（行为变化）—— ❌ 新增（已知取舍）

- **位置**：`components/easytier-esp/src/config/settings.hpp` 的 `Settings`；
  `config/toml.cpp` 的字段赋值（如 `out.network_name = value;`）
- **证据**：组件以 `-fno-exceptions` 编译；`std::string`/`std::vector` 分配失败会走
  `std::terminate`。TOML 解析器在分配失败或语法树超限时仍返回 `ESP_ERR_NO_MEM`
  （`toml.cpp` 的 "out of memory" 判定与语法树限额分支），但**字段级分配失败不再有错误码**；
  TOML 文本已无长度上限、也无解析堆预算（`EASYTIER_ESP_TOML_MAX_BYTES` 与
  `EASYTIER_ESP_TOML_HEAP_BUDGET` 均已删除）
- **影响**：极端 OOM 下表现为 abort，而不是"构造失败 + `last_error()`"
- **建议**：这是用户明确选择的实现方式（用 `std::string` 的 SSO）。若将来要恢复
  可恢复错误，需要在公开文档中注明，或对少数长字段改用 `nothrow` 容器
- **风险**：接受

### F4. `Context::get_config_info()` 的 3600 B 栈帧（新暴露）—— ❌ 新增

- **位置**：`components/easytier-esp/src/context.cpp` 的 `Context::get_config_info()`；
  `out = ConfigInfo{};` 产生约 3.5 KiB 的栈临时对象
- **证据**：本次 `-fstack-usage` 实测该函数帧 **3600 B**（组件内第二大帧，仅次于
  `et::proto_task` 的 4608 B）
- **影响**：调用方必须有大栈。示例里唯一调用点是
  `main/easytier_app.cpp:138`（`log_effective_config()`，由 8 KiB 的 `et_start` 任务调用），
  当前安全；但 **esp_timer 任务栈只有 3584 B**（`sdkconfig:2088`），
  一旦将来从 `status_timer_cb` 里调用 `get_config_info()` 就会栈溢出
- **建议改法**：避免 `out = ConfigInfo{}` 的整对象临时（逐字段写或将 `ConfigInfo`
  改为调用方先清零的小粒度接口）；至少在公开头注释里写明"需要约 4 KiB 空闲栈"
- **风险**：低（当前调用点安全），但属易踩的坑

### F5. 公开头前向声明了内部类型 `et::Context` —— ❌ 新增（轻微）

- **位置**：`components/easytier-esp/include/easytier-esp.h:221`（`struct Context;`）
- **证据**：`Inst` 私有持有 `Context* ctx_`（`:363`），因此公开头必须前向声明它。
  类型定义仍在内部 `src/context.h`，不暴露 FreeRTOS/lwIP 头，也不受 92,808 B 影响
- **影响**：`et::Context` 这个名字出现在公开命名空间里（不完整类型），有轻微命名污染；
  用户若自己声明 `et::Context` 可能冲突
- **建议改法**：可选——改用 `void*` + 内部转换，或把成员包进一个私有前置声明类型；
  但当前代价极低，建议保留并接受
- **风险**：接受

### F6. 并发构造会被拒绝（`ESP_ERR_INVALID_STATE`）—— ❌ 新增（需文档化）

- **位置**：`components/easytier-esp/src/config/toml.cpp` 的 `g_parse_busy`
  非阻塞标记
- **证据**：tomlc17 的全局选项（UTF-8 校验/分配器）是进程级状态，首次安装需要串行；
  已有解析进行中时第二次构造直接返回 `ESP_ERR_INVALID_STATE`。
  文档已在 README/AGENTS 写明"构造必须串行"
- **影响**：多实例场景下，若两个任务并发构造 `Inst`，第二个会失败（而不是排队或崩溃）
- **建议**：保持现状（fail-fast 比并发安装全局选项更安全）；已记录在文档中
